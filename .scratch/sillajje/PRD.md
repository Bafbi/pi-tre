# Sillajje — Auto-versioning for Pi agent sessions

## Problem Statement

Pi agent sessions have no built-in version control. When an agent makes file edits across multiple turns, there is no automatic record of what changed, why, or in what order. Reviewing agent work after the fact requires manually scanning the session transcript. There is no way to undo a single interaction without losing everything after it, and no way to understand the sequence of changes an agent made across sessions. The user must remember to commit manually — breaking their flow and placing the burden of discipline on the human.

## Solution

Sillajje is a Pi extension that automatically versions every agent interaction as a jj change. It creates an isolated jj workspace per Pi session, redirects all agent file operations there, and on every `agent_settled` event stamps a jj change with: a conventional-commit subject line, the user's prompt, programmatic metadata (tools used, call count, elapsed time), an AI-generated summary of the interaction, and the agent's final response. The result is a complete, reviewable trail — a *sillage* — of every interaction via standard jj tooling (`jj log`, `jj show`, `jj diff`). Sessions can be archived (workspace deleted, bookmark kept) and unarchived to reclaim disk space without losing history.

## User Stories

1. As a Pi user, I want every agent interaction automatically recorded as a version control change, so that I never lose work or forget to commit.
2. As a Pi user, I want to run `jj log` and see a timeline of all agent interactions with conventional commit subjects, so that I can understand the history at a glance.
3. As a Pi user, I want to run `jj show <change>` and see the full context of an interaction — what I asked, what tools the agent used, a summary of what it did, and its response — so that I can review past work without opening session transcripts.
4. As a Pi user, I want to run `jj diff -r <change>` and see exactly what files the agent modified in a specific interaction, so that I can inspect code changes.
5. As a Pi user, I want agent sessions isolated from my main working tree, so that experimental or in-progress work doesn't pollute my repo until I'm ready to merge it.
6. As a Pi user, I want the extension to be invisible when jj is not installed or the repo is not jj-initialized, so that it never gets in the way.
7. As a Pi user, I want to archive old sessions to reclaim disk space while keeping their bookmarks for traceability, so that I can manage storage without losing history.
8. As a Pi user, I want to unarchive a session and resume working in it, so that I can pick up where I left off days later.
9. As a Pi user, I want archived sessions to block new prompts until unarchived, so that I don't accidentally work in a session whose workspace no longer exists.
10. As a Pi user, I want the commit subject and summary generated by a cheaper/faster model than my main session, so that I don't waste expensive context on metadata.
11. As a Pi user, I want mid-stream steering corrections to fold into the same interaction's change rather than creating spurious new changes, so that the log reflects meaningful boundaries.
12. As a Pi user, I want session bookmarks to be purely local and never auto-pushed, so that my experimental work doesn't clutter the remote.
13. As a Pi user, I want the extension to notify me clearly when an error occurs (e.g., sub-generator failure, missing jj binary), so that I know something went wrong rather than silently missing history.
14. As a Pi user, I want each session to start from the current working-copy commit (`@`) so that the agent works from exactly where I am, including local commits ahead of the remote trunk.
15. As a developer reviewing agent work, I want the commit body to contain the user's original prompt, so that I can understand why a change was requested.
16. As a developer resuming work after a break, I want the commit body to contain a structured summary of what the agent did, so that I can catch up without re-reading the transcript.
17. As a Pi user, I want the footer to show sillajje session state at a glance (active/archived, workspace path or bookmark), so that I don't need to run `/sillajje status` to know what's happening.

## Implementation Decisions

### Session lifecycle state machine

A sillajje session is in exactly one of three states, derived from jj workspace and bookmark presence:

- **Inactive** — no jj repo, or jj not on PATH. Extension no-ops; all handlers are transparent pass-throughs.
- **Active** — workspace directory exists on disk, bookmark `sillajje/<session-id>` exists, system prompt is patched, tool-call path redirection is active. Prompting is allowed.
- **Archived** — bookmark exists but workspace directory is absent. Prompting is blocked via an `input` event handler that returns `{ action: "handled" }` with a notification.

Transitions: `session_start` checks state → creates workspace if absent (inactive → active). `/sillajje archive` deletes workspace directory + `jj workspace forget` (active → archived). `/sillajje unarchive` recreates workspace + `jj workspace add` (archived → active).

### Extension events wired

The extension hooks five Pi events:

- `session_start` — detects jj availability, determines repo root, creates workspace from `trunk()`, sets up state tracking.
- `before_agent_start` — injects system prompt patching the agent's working directory to the workspace path. No-op if inactive.
- `agent_settled` — on new interactions (not steering), snapshots working copy, builds metadata, spawns sub-generator, stamps jj change with full commit body, sets bookmark. No-op if inactive.
- `tool_call` — rewrites paths for `read`/`write`/`edit` to absolute workspace paths; wraps `bash` with `cd <workspace> &&` prefix. No-op if inactive.
- `input` — blocks prompts on archived sessions with a notification. Passes through otherwise.

### Interaction boundary

A new interaction starts when the user sends a prompt with `streamingBehavior` other than `"steer"` (i.e., `undefined` for fresh prompts, `"followUp"` for queued messages). Mid-stream steering corrections (`streamingBehavior: "steer"`) are part of the current interaction and do not create a new change. The change is created on the next `agent_settled` after a new interaction begins.

### Commit body structure

```
<conventional-commit subject line — agent actions, generated by sub-generator>

<User prompt>

<Metadata block — programmatic>
tools_used: read, write, bash
tool_calls: 14
elapsed: 45.2s
thinking_blocks: 3
workspace: sillajje/<session-id>
generated_by: sillajje

<AI-generated summary of agent interaction — generated by sub-generator>

<Agent's final text response>
```

### Sub-generator

A headless `pi -p` process spawned via `child_process.spawn`. Configured with a cheaper model (`sillajje.sub-generator-model`). Receives a mustache-templated prompt containing: the session transcript (user messages + agent tool calls + agent responses, sans tool outputs), the file diff, and previous change descriptions as compressed context. Outputs structured text: subject line on line 1, summary in the remainder.

Two-template vs one-template approach to be determined by testing — a single pi process may generate both subject and summary, or two separate calls may yield better results.

### Workspace isolation

Workspaces live at `~/.pi/sillajje/<repo>/<session-id>/` (configurable via `sillajje.workspaces-root`). Each is created from the current working-copy commit (`@`) via `jj workspace add --revision @`. This means sessions start from whatever branch/commit the user is on — including local commits ahead of the remote trunk. The agent's cwd cannot be changed by the extension (Pi limitation), so path redirection is used: `read`/`write`/`edit` inputs get absolute workspace paths, `bash` commands get a `cd <workspace> &&` prefix. The system prompt informs the agent of its workspace path.

Gitignored files are absent from workspaces. Repos must be reproducible via mise for dependencies and tooling.

### Bookmarks

Each session gets a local bookmark `sillajje/<session-id>` set to the working-copy commit after each change is stamped. Bookmarks are never auto-pushed to remotes. Kept on archive for traceability.

### Archive and unarchive

**Archive:** `jj workspace forget <name>` + `rm -rf <workspace-path>`. Bookmark persists. Manual only, no auto-archive.

**Unarchive:** `jj workspace add --name sillajje-<session-id> --revision sillajje/<session-id> <path>`. Workspace recreated, system prompt re-patched, tool handlers re-enabled.

### Footer status pill

The extension sets a status pill on the footer extension-status line via `ctx.ui.setStatus("sillajje", text)`. The pill format depends on lifecycle:

- **Active:** `sillajje: [active] <shortened-workspace-path>` — path shortened the same way the footer shortens cwd (`~` for home, relative otherwise).
- **Archived:** `sillajje: [archived] sillajje/<session-id>` — the bookmark name since the workspace directory is gone.
- **Inactive:** pill is cleared (no status set).

The pill updates on every lifecycle transition: `session_start`, `/sillajje archive`, and `/sillajje unarchive`.

### Commands

Single command `/sillajje` with subcommands:

- `/sillajje archive [session-id]` — archive a session (defaults to current)
- `/sillajje unarchive <session-id>` — unarchive a session
- `/sillajje status` — show current session state (active/archived/inactive, workspace path, bookmark)

### Module design

Internal modules with deep interfaces:

- **session.ts** — central orchestrator. Callers (index.ts event handlers) delegate here. Hides workspace, sub-generator, metadata, and path-redirect modules behind a small surface: `init`, `blockIfArchived`, `onSettle`, `archive`, `unarchive`, `status`.
- **workspace.ts** — jj workspace CRUD. Interface: `create`, `status` (active/archived/absent), `archive`, `unarchive`.
- **sub-generator.ts** — spawn headless pi, parse structured output. Interface: `generate(context) → { subject, summary }`.
- **metadata.ts** — pure function: `build(interaction) → string`.
- **path-redirect.ts** — pure function: `redirect(event, workspacePath) → void` (mutates event.input in place).
- **state.ts** — session state tracking across the extension lifecycle.

### Architecture Decision Record

ADR-0001 records the choice of workspace isolation via separate jj workspaces + path redirection over colocated work. See `extensions/sillajje/docs/adr/0001-workspace-isolation.md`.

### Configuration

```toml
[sillajje]
sub-generator-model = "openai/gpt-4o-mini"
workspaces-root = "~/.pi/sillajje"
```

## Testing Decisions

### What makes a good test

Tests exercise external behavior through module interfaces, not implementation details. Pure functions are tested with table-driven inputs/outputs. Stateful modules are tested by exercising their public methods and asserting observable state changes. Integration tests fire synthetic Pi events through `ExtensionRunner` and assert handler behavior (blocking, path rewriting, command registration) — matching the pattern established by `stale-write-guard/test/integration/extension-runner.test.ts`.

### Modules tested

- **Unit (vitest):** `metadata.ts` (pure, table-driven), `path-redirect.ts` (pure, mock event shape), `state.ts` (class with assertions, like `FileTrackingStore`), `workspace.ts` (mock `runJj` adapter), `sub-generator.ts` (mock `runSubPi` adapter).
- **Integration (ExtensionRunner):** Load the full extension, fire `session_start`/`before_agent_start`/`agent_settled`/`tool_call`/`input` events, assert CWD-relative path rewriting, assert commands registered, assert archived sessions block input, assert inactive no-ops.

### Prior art

Follows the test structure of `stale-write-guard`: unit tests for pure modules (`test/unit/`), integration tests via `ExtensionRunner` for event handler behavior (`test/integration/`).

## Out of Scope

- Auto-pushing bookmarks or changes to remotes
- Conflict resolution between sillajje workspaces and user changes
- Merging sillajje changes back into the user's working tree (the user does this manually via `jj`)
- Auto-archiving based on age or disk pressure
- A TUI dashboard or custom rendering for reviewing changes (standard jj tooling suffices)
- Support for non-jj VCS backends
- Integration with Pi's `/compact` or `/tree` for generating summaries on those events
- Generating summaries for consumption by future sessions (the sub-generator uses prior descriptions, but no session-context injection yet)

## Further Notes

- The extension name "sillajje" is a portmanteau of the French "sillage" (wake, trail) and "jj" — the trail of changes an agent leaves behind.
- The domain glossary is in `extensions/sillajje/CONTEXT.md`.
- Session ID is derived from `ctx.sessionManager.getSessionId()`.
- The extension is registered in the monorepo root `package.json` `pi.extensions` array.
- Prompt template uses mustache syntax for the sub-generator.
