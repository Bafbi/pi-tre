Guard the whole-file write, not the edit

The guard should stop blocking edit. Its exact-text match is the freshness check; only write needs a read record.

2026-10-24 stale-write-guard research session 01a162b9
Summary Recommendation Evidence Research answers Trade-offs Test cases Follow-ups

Summary

The guard's read detection is not the root cause of the session's 82% bash-write bypass. The root cause is that the guard applies an mtime rule to edit, a tool that already re-reads the file and refuses to apply an edit unless every oldText matches a unique region. Widening the parser to accept sed and pipes would hide more of the symptom, but it would also record partial reads as full reads and keep the same false blocks for the next command shape it does not understand.

Recommendation: split the contract. edit never blocks. write blocks until the agent has read the whole current file. Shrink the bash reader to cat only, because only a full file view qualifies for a whole-file overwrite. Treat bash writes as outside the guard and say so in the README.

This removes every observed edit block without adding a parser case. It also closes an existing hole: today a head -n 5 or a partial read lets the agent overwrite the rest of the file.

Implemented 2026-10-24. edit is no longer gated; write requires a full read; the bash parser accepts only a bare cat, resolves operands literally, and drops paths after a cd/pushd/popd segment. mise run //extensions/stale-write-guard:check passes 68 tests, and the per-extension ci scan is clean.

Recommendation

The new contract

ToolTodayProposedWhy
edit Blocked without a read record for the current mtime. Never blocked by this guard. The edit tool reads the file, matches every oldText exactly or fuzzily, and errors on a missing or duplicate match. The match proves the edited region is current.
write Blocked unless any read record matches the current mtime. Blocked unless a full-content read record matches the current mtime. write replaces the whole file and has no content check. A partial read does not prove the unseen part is current.

What counts as a full read for write

  • read with no offset, no limit, and no truncation. The read tool caps at 2,000 lines or 50 KB; a truncated result is not full.
  • cat with no pipeline, no redirect, no command substitution, no flag, and no truncated bash output. Operands resolve literally: a leading @ stays and ~ is not expanded. A cd/pushd/popd before the cat drops every later path.
  • A /skill:name block or a session context file whose disk content still matches the injected content.

What does not count

sed -n, awk, head, tail, grep, rg, rg -A/-B, jj diff, git diff, and any reader-side pipe. They show part of the file, a transformed view, or a diff. They do not prove the whole current file reached context. Under the split they do not need to count for edit, because edit is not gated.

Block reason

Replace the current message, which names neither the tool nor the missing condition:

File 'X' was not fully read at its current version. A write replaces the
whole file, so read it first with the read tool (no offset/limit). For
targeted changes, use edit, which checks the exact text.

Implementation sketch

// state: canonical path -> mtime of the last full-content read
const fullyReadMtimeMs = new Map<string, number>();

pi.on("tool_call", async (event, ctx) => {
  if (!isToolCallEventType("write", event)) return undefined;
  // ... resolve path, stat current mtime ...
  if (requiresFullRead(currentMtimeMs, fullyReadMtimeMs.get(canonicalPath))) {
    return { block: true, reason: ... };
  }
});

pi.on("tool_result", async (event, ctx) => {
  if (event.isError) return undefined;
  // read: record only when full
  // write: record (the agent authored the whole file)
  // edit: do not record; the mtime check will invalidate the old full read
  // bash: record cat only, and only when the output was not truncated
});

An edit changes the mtime, so any previous full-read record becomes stale automatically. A later write then needs a fresh full read. This is conservative and needs no extra state.

Do not widen the parser to sed, awk, or pipes while keeping the edit block. That direction treats a 40-line sed range as a full read, keeps the false block for the next unparsed shape, and weakens the write gate it claims to protect.

Code facts

  • src/index.ts records every successful read result, including results with offset/limit and truncated results. It never inspects details.truncation. (src/index.ts:160-175)
  • src/bash.ts accepts cat, head, tail, tac, nl, bat, grep, and rg, and returns nothing for any segment containing |, <, >, or &. (src/bash.ts:11-21, 75)
  • The edit tool reads the file, tries exact oldText match, then a fuzzy match, and throws when the text is missing or non-unique. It never overwrites an unseen region outside the matched text. (@earendil-works/pi-coding-agent/dist/core/tools/edit.js, edit-diff.js)
  • The read tool supports offset/limit and truncates at 2,000 lines or 50 KB. The ticket cites a 2,866-line file; a full read of that file is not one call. (dist/core/tools/read.d.ts, truncate.d.ts)
  • The existing tests codify the false block: blocks edit on existing file when no read record exists, blocks edit when file changed externally after last agent edit, and the sed/pipe cases in test/unit/bash.test.ts.

Research answers

QuestionAnswer
Which command shapes should count as a read? For write, only full-content views: read with no offset/limit and no truncation, cat with no pipe or redirect and no truncation, and injected content whose disk file still matches. sed -n, awk, head/tail ranges, grep/rg, diffs, and reader-side pipes do not count. They are partial or transformed. They do not need to count for edit.
Is a partial read enough to permit an edit? Yes. The edit tool re-reads the file and matches oldText uniquely. The match proves the edited region is current; a partial read is enough because the tool verifies the exact region. The guard's mtime check adds no information for edit.
Should edit and write have different strictness? Yes. write replaces the whole file with no content check, so it needs a full read. edit has its own exact-match check, so it needs none. This is the core of the recommendation.
What is the false-positive cost of recording a read when the content was printed through a pipe? Under the old model, the cost is a stale whole-file write: the pipe may filter or transform, so the file's current content did not fully reach context, but the guard records it as a full read. Under the split, the cost is zero because edit does not use records and write does not accept piped output.
Can a bash write to a source file be surfaced without blocking legitimate bulk edits? Yes, without parsing the command: snapshot tracked mtimes at bash tool_call, stat again at tool_result, and append a short note for each tracked file whose mtime changed. This does not block. It is a useful follow-up, but not the primary fix. Blocking bash writes would break bulk edits and invite another bypass.
If the guard records more reads, does it still prevent the stale overwrite it was built for? For write, only if the record is a truthful full read. Recording more partial reads weakens the gate because a parser mistake can whitelist a whole-file overwrite over an external change. For edit, the tool's exact match prevents the overwrite regardless of what the guard records.

Trade-offs

edit loses the mtime gate

The guard no longer catches a stale edit before the tool runs. The edit tool still catches it: a changed region fails the oldText match. Fuzzy matching can overwrite an external whitespace or quote normalization change inside the edited region. That is a cosmetic risk, not a whole-file overwrite.

Large-file writes stay blocked

The read tool caps at 2,000 lines or 50 KB, so a file above that cap cannot get a full-read record in one call. The agent must use edit or read in a way the guard can verify. Range-coverage tracking is the follow-up if full rewrites of huge files become a real workflow.

Bash writes remain outside the guard

python3, perl -i, sed -i, and cat > are not gated. That was already true. The guard cannot parse arbitrary write scripts reliably. Document the boundary instead of pretending the guard covers them.

The guard gets smaller

bash.ts shrinks to cat only. The reader set, the pattern-reader rule, and the ambiguity around pipes and redirects go away. Fewer records mean fewer chances a parser bug whitelists a stale write.

Residual race. The write gate stats the file at tool_call and the tool writes later. An external change that lands between the stat and the write is not caught. The edit tool has the same read-match-write window. No mtime check can close it without a lock. The 2 ms tolerance also means a change within 2 ms of the read can be missed. Both are small windows, but they are not covered by the tests above.

Test cases that would prove it

All integration tests use the extension runner in test/integration/extension-runner.test.ts and set mtimes with utimesSync far enough apart to clear the 2 ms tolerance.

Follow-ups

  • Update the docs. README.md and AGENTS.md currently say the guard blocks both tools and that a missing record “only costs an extra read.” Change them to: edit is not gated; write needs a full read; bash writes are outside the guard.
  • Coverage tracking, if needed. If whole-file rewrites of files above the 2,000-line read cap become common, record read ranges per mtime and allow write once the ranges cover the file. Do not add this before the split; the simple full-read rule covers the observed session.
  • Non-blocking bash-write note. Snapshot tracked mtimes at bash tool_call and compare at tool_result. Append a short note naming the tracked files the command changed. This surfaces the bypass without blocking bulk edits. It is optional.
  • Do not block bash writes. A blocklist for python3, perl -i, sed -i, and cat > will miss the next writer and break legitimate bulk edits. The right place for that policy is a permission layer, not this guard.
