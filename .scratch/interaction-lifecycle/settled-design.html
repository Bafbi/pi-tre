Interaction lifecycle: settled design

The session log is the source of truth. agent_settled is the trigger. The state machine has nothing left to own.

Design: log projection

Keep one piece of lifecycle state: a cursor into the session log. Derive everything else.

State

// Reconstructed from the branch, not authoritative in memory.
let cursorId: string | null = null;   // id of the last "sillajje/stamp" custom entry

Pure projection (unit-testable with entry fixtures)

type Projection =
  | { interaction: InteractionData; throughId: string; leafId: string }
  | undefined;

function projectInteraction(branch: SessionEntry[], cursorId: string | null): Projection {
  const start = cursorId === null
    ? -1
    : branch.findIndex((e) => e.id === cursorId);
  const entries = branch.slice(start + 1);
  const messages = entries
    .filter((e): e is SessionMessageEntry => e.type === "message")
    .map((e) => e.message);
  const interaction = deriveInteractionData(messages);
  if (!interaction) return undefined;
  return { interaction, throughId: entries.at(-1)!.id, leafId: branch.at(-1)!.id };
}

At settle the run is complete, so no error/defer/final-turn logic is needed. Retries are already folded into one branch slice. deriveInteractionData takes the first user prompt and the last assistant response, so a mid-slice error message does not corrupt the result.

Handlers

// Reconstruct the cursor on load and after branch navigation.
const syncCursor = (ctx) => {
  cursorId = lastStampMarkerId(ctx.sessionManager.getBranch());
};
pi.on("session_start", syncCursor);
pi.on("session_tree", syncCursor);

// The one stamp trigger.
pi.on("agent_settled", async (_event, ctx) => {
  if (skip(ctx)) return;
  await stampPending(ctx);
});

// Flush on the way out.
pi.on("session_shutdown", async (_event, ctx) => {
  if (skip(ctx)) return;
  await stampPending(ctx);
  // ... existing unused-workspace archive
});

async function stampPending(ctx) {
  const branch = ctx.sessionManager.getBranch();
  const projected = projectInteraction(branch, cursorId);
  if (!projected) return;

  const result = await buildStamp(ctx).session({
    target: sessionKey, current: { sessionKey, wsPath },
    interaction: projected.interaction,
  });

  // Advance the cursor whether the stamp succeeded, failed, or found no changes.
  pi.appendEntry("sillajje/stamp", { rev: result.ok ? result.rev : null });
  cursorId = ctx.sessionManager.getLeafId();
}

Why this is the pi-shaped answer

  • The session log is the state. getBranch() is branch-correct by construction, matching pi's own state-management guidance (docs/extensions.md:1860).
  • The trigger is pi's own completion signal. agent_settled exists precisely for integrations that must know pi will not continue.
  • Persistence is pi's own mechanism. appendEntry is the documented way to store extension state that survives reload.
  • Two pi examples already do this. git-checkpoint.ts clears state on agent_settled; auto-commit-on-exit.ts commits on session_shutdown after reading the last assistant message from getEntries().

Deleted

Everything in SessionState's interaction section, plus the handler fragments:

  • Fields: newInteraction, messages, lastRunEndedInError, lastStreamingBehavior, pendingFinalize.
  • Methods: startInteraction, hasNewInteraction, hasPendingFinalize, markPendingFinalize, clearPendingFinalize, enableInteractionIfNotSteering, recordAgentMessages, recordAgentEndError, lastAgentRunWasError, getInteractionMessages, resetInteraction.
  • Handlers: the agent_start handler; the interaction branch in agent_end; the pending-flush blocks in input and session_shutdown; the prompt-recording and enableInteractionIfNotSteering in before_agent_start.

Replaced by one cursor and one pure function. The proposed state machine from the original recommendation is not needed.

Alternatives, and why not

DesignShapeVerdict
A. Settle + accumulate Keep recordAgentMessages; move the stamp from agent_end to agent_settled; delete the defer machine. Smallest safe change. Good fallback if the session read feels risky. Loses the reload-safety and branch-correctness of the log projection.
B. Settle + session read, no persistence Read getBranch() at settle; keep the cursor only in memory. No better than the projection and loses recovery after a reload mid-interaction. Reject.
C. Final-turn trigger Stamp at the final turn_end (assistant message with no tool call, not error/aborted). Gives a follow-up its own change. Only worth it if strict one-change-per-follow-up is required. Needs careful handling of retries, length, and mid-run sealing. See the follow-up section.
D. State machine The original recommendation: one module owning transcript, steer, defer, and the stamp decision. Superseded. It centralizes a rule that agent_settled makes unnecessary.

Follow-up decision

Pi treats a follow-up as part of the current run: it is drained before the final agent_end and never fires before_agent_start. So settle-only stamping yields one change per run, and a follow-up folds into the current change.

Recommended: accept one change per run. It matches pi's model, needs no extra events, and the change still contains the full transcript of both prompts and all tool work. It also fixes the synthetic test rather than preserving a behavior pi does not produce.

If strict separation is required, add Design C: detect the final turn at turn_end and stamp there, before the follow-up is injected. The detection rule must exclude stopReason error and aborted; length needs a decision because pi may compact and retry. This is more moving parts for a rare case.

Open

  • Confirm the trigger live. One log line in a real TUI session. The source, docs, changelog, and upstream test all agree; this closes it.
  • Follow-up semantics. One change per run (recommended) or per follow-up (Design C). This changes the test suite.
  • Marker id vs throughId as the cursor. Both work. Using the marker's own id (getLeafId() after appendEntry) is simplest; storing throughId in the data is a good provenance backup.
  • Cursor when the branch no longer contains the marker. After a fork or tree navigation the last marker may be absent. Fall back to null (treat the whole branch as new) and decide whether re-stamping old messages is acceptable.
  • Failed-stamp policy. Advance the cursor and record the failure, matching today's "reset even on failure", or leave the cursor to retry on the next settle.
  • Sequencing. Do this after the check gate is green (mise run check-baseline), as noted in the first report.
