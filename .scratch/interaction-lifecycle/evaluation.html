Interaction lifecycle: evaluation

The diagnosis holds. The cure is right in direction, under-specified in two places, and oversells the test payoff.

2026-09-23 scope: extensions/sillajje + @pi-tre/sillajje-core verdict: valid, revise before implementing
Summary What holds What does not Pros and cons Alternatives Open questions

Summary

The recommendation is valid as a diagnosis and worth doing as a refactor, but it is not ready to implement as written. It correctly names the problem: interaction-scoped state and the rule that acts on it are split between state.ts and five pi handlers plus stampChange. Two claims need correction, and one design decision is left open.

  1. The seam is incomplete. The proposed vocabulary onPrompt · onAgentStart · onAgentEnd · takeForStamp has no slot for before_agent_start (records the prompt, enables the interaction) or session_shutdown (flushes a pending interaction). Those are two of the five handlers the recommendation says it is consolidating.
  2. The type boundary contradicts itself. The module cannot "own the transcript" and "never take pi types" at once, because the transcript is Message[] until deriveInteractionData runs at stamp time. The recommendation must pick: the module holds a structural message type and owns derivation, or the adapter keeps the transcript and the module owns only flags and timing.
  3. The test payoff is real but modest. stampChange already centralizes the decision body; the scatter is in the triggers and the flags. Roughly 250 of the 924 lines in change-stamping.test.ts cover lifecycle timing. Even after extraction, one end-to-end wiring test must stay, because the guarantee ("a partial interaction is never sealed") is a jj-level fact no unit test can assert.

The best form is a small state machine that owns the interaction-scoped state and returns an explicit decision, which also removes about 100 lines from SessionState. Do it after the check gate is green.

What holds

State and rule are separated

state.ts is 294 lines of getters and setters. Interaction-scoped fields — newInteraction, messages, lastRunEndedInError, lastStreamingBehavior, pendingFinalize — live beside session-scoped fields like repoRoot, workspacePath, and lifecycle. The two concerns share one holder.

The deferral rule is subtle and spread out

The rule "an error agent_end is not the end of the interaction" is stated in a long comment on pendingFinalize, enforced in agent_end, cleared in agent_start, and consumed in input and session_shutdown. Reading one of those does not explain the others. This is the strongest argument for the change.

Illegal flag combinations are implicit

pendingFinalize implies lastRunEndedInError, which implies newInteraction, which implies non-empty messages. Nothing encodes that. A state machine makes the legal states finite and the transitions explicit.

The deletion test is applied correctly

The recommendation notes that deleting SessionState alone would only move fields, and that the deepening is the state machine. That is the right reading.

What does not

1. The seam drops two of the five events

The recommendation's own problem statement lists five handlers: input, before_agent_start, agent_start, agent_end, session_shutdown. The proposed interface lists four methods and omits two of them.

  • before_agent_start does two interaction things: it appends the user prompt to the transcript, and it calls enableInteractionIfNotSteering() as a fallback for queued follow-ups that bypass input. Both must move into the module.
  • session_shutdown calls stampChange when hasPendingFinalize(). The module needs a flush entry point.

A seam that misses events cannot become the single home for the rule.

2. "Owns the transcript" and "never pi types" cannot both be true

The module must accumulate messages across retry segments and derive InteractionData only at the end. Derivation needs every message: response is the last assistant message, elapsedMs is last minus first timestamp, and tool names are unioned across all assistant messages. So the transcript has to live somewhere until takeForStamp.

Today the core boundary already speaks InteractionData, not Message[] (see packages/sillajje-core/src/stamp/types.ts). That is the right boundary. But the lifecycle module sits on the pi side of it and needs the raw entries. The clean resolution is a local structural type:

type InteractionMessage = { role: string; content: unknown; timestamp: number };

The module owns InteractionMessage[] and the derivation. The adapter converts pi Message[] to InteractionMessage[] at the edge. This is a real change to derive.ts, not a detail the recommendation can skip.

3. The scatter is smaller than stated

stampChange already holds the decision body: check session and workspace, check hasNewInteraction, fetch messages, derive, call the action, reset. The five handlers only hold triggers and flag writes. Moving the flags and the decision into a module concentrates the rule, but the handlers do not contain "five fragments of the decision" as the text implies. The win is real; the size is smaller.

4. The test claim is half true

test/unit/state.test.ts already unit-tests the flag mechanics — steer, follow-up, pending mark/clear/reset — in 358 lines. What is only end-to-end is the decision to act: that an error agent_end defers, that a retry resumes, that a next prompt flushes. Extracting the module moves those decisions to plain-data tests. But the three deferral tests in change-stamping.test.ts also assert jj facts (the sealed change contains a.ts and b.ts, not a partial set). Those assertions cannot move. Expect to move the decision assertions and keep a smaller integration test.

5. Timing against the red gate

AGENTS.md states the gate is temporarily red: typecheck-tests, typecheck-strict, //:lint, //:knip, //:ast-grep, and leaf-copy:test fail on findings the in-progress refactor owns. Adding a structural refactor on top makes a new failure hard to attribute. Sequence it after mise run check-baseline is clean.

Pros and cons

DimensionProCon
Locality One file answers "when does an interaction stamp?" The error/defer/retry rule gets one home. Adds a second holder beside SessionState; the boundary between session state and interaction state must be drawn and kept.
Correctness An explicit phase removes illegal flag combinations. The steer-preserves-live subtlety becomes a transition, not a comment. The current code is correct and freshly fixed (commit 3045039). A rewrite risks regressing a rule that just landed.
Tests Decision tests run over plain data, no runner, no jj, no sub-generator mock. Only the decision assertions move. The end-to-end wiring test and the jj content assertions stay. Net suite reduction is small.
Leverage A new settle signal or queue rule changes one interface instead of five call sites. No such rule is pending. The leverage is speculative; the churn is immediate.
Type boundary Aligns with the existing direction: the core never sees pi types. Requires derive.ts to work over a structural message type, which the recommendation does not budget.
Placement The rule is host-agnostic and could live in @pi-tre/sillajje-core. The event names are pi-shaped and no second host exists. Core placement is a premature package boundary.

Alternatives

Four shapes, from smallest to largest.

A. Pure decision function, state stays in SessionState

type Decision =
  | { kind: "stamp"; messages: InteractionMessage[] }
  | { kind: "defer" }
  | { kind: "none" };

function decide(event: LifecycleEvent, view: InteractionView): Decision;

Handlers call decide, then apply the result. Pros: smallest change, trivially unit-testable, no new holder. Cons: state and rule stay in different files, which is the original complaint. This is the minimum that answers "why didn't it stamp?" from one function.

B. State machine that owns interaction state (recommended)

type Phase = "idle" | "live" | "errored";

class Interaction {
  onPrompt(behavior: string | undefined): Decision;
  onBeforeAgentStart(prompt: string): void;
  onAgentStart(): void;
  onAgentEnd(messages: InteractionMessage[], stopReason?: string): Decision;
  flush(): Decision;                       // session_shutdown
  consume(): InteractionData | undefined;  // after a stamp
}

SessionState drops the five interaction fields and their methods, about 100 lines. The adapter keeps only session lifecycle, and each handler becomes one call plus a switch on the decision. This is the recommendation done properly: the module owns the state, the decision is explicit, and consume makes the "reset even on failure" contract visible.

consume must run whether the stamp succeeded, failed, or returned no-changes. Today the code resets in all three cases. If the interface hides that, a future change will reintroduce a stale-transcript bug. Name the method so the contract is obvious, and test all three outcomes.

C. Pure reducer

type Event =
  | { type: "prompt"; behavior?: string }
  | { type: "beforeAgentStart"; prompt: string }
  | { type: "agentStart" }
  | { type: "agentEnd"; messages: InteractionMessage[]; stopReason?: string }
  | { type: "flush" }
  | { type: "stamped" };

function reduce(state: InteractionState, event: Event): [InteractionState, Effect];

Pure, deterministic, the easiest to test and to reason about. Cons: an effect channel is more machinery than this codebase uses anywhere else, and SessionState is an imperative class. It is the more correct option and the less idiomatic one. Prefer B unless you expect the state space to grow.

D. Leave it, do a targeted cleanup

The deferral rule is correct, freshly fixed, and well-commented. The real defect is that interaction state shares a holder with session state. A smaller move — split SessionState into SessionState and a plain InteractionState holder, no behavior change — captures most of the locality without touching the handlers. Then extract the decision function later. This is the lowest-risk option while the gate is red.

Open questions

  • Where does the module live? Extension (extensions/sillajje/src/interaction.ts) until a second host exists, or @pi-tre/sillajje-core now? The events are pi-shaped; the rule is host-agnostic. Extension is the smaller commitment.
  • Does the module own derivation? If yes, derive.ts moves or becomes generic over InteractionMessage. If no, the module owns flags and timing only, and the transcript stays in the adapter. The first is cleaner; the second is less churn.
  • Imperative class or reducer? B matches the codebase; C is purer. Pick based on whether more lifecycle rules are coming.
  • When? Now, or after mise run check-baseline is clean? The recommendation does not address the red gate.
