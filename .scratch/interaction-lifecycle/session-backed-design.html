Session-backed interaction: a smaller design

Stamping on agent_settled and reading the transcript from the session deletes the defer state machine instead of extracting it.

2026-09-23 pi-coding-agent 0.84.4 extends: interaction-lifecycle/evaluation.html
Summary Evidence Design A Design B What gets deleted Caveats Open questions

Summary

The original recommendation says to give the lifecycle a module. The adapter already provides a better primitive: agent_settled fires once, after retries and compaction, and the session manager exposes the full append-only transcript. Use both and the defer machinery has nothing left to do.

  • Design A (smallest): keep accumulating messages in agent_end, move the stamp trigger to agent_settled. Delete pendingFinalize, lastRunEndedInError, the error branch, clearPendingFinalize, and the two pending-flush call sites. No session read, no derive.ts change.
  • Design B (full): also drop message accumulation and read the interaction from ctx.sessionManager.getBranch() at settle. This removes the last interaction field. Requires a boundary marker.

Design A is the better first move. It is a small diff with the whole correctness win, and it does not depend on getting the session slice right.

Design A: move the trigger, delete the defer machine

Keep the transcript accumulation exactly as it is. Change only when the stamp fires.

// agent_end — accumulate only. No error branch, no defer.
pi.on("agent_end", async (event) => {
  if (skip()) return;
  state.recordAgentMessages(event.messages as Message[]);
});

// agent_settled — the one true end. Stamp if there is anything to stamp.
pi.on("agent_settled", async (_event, ctx) => {
  if (skip()) return;
  await stampChange(ctx);
});

Why this is enough: the error agent_end accumulates the error message and returns; agent.continue() runs the retry; its agent_end accumulates the retry segment; the finally emits one agent_settled. The accumulated transcript spans all segments, exactly as the current defer logic tries to reconstruct.

Deleted in Design A:

  • pendingFinalize field, hasPendingFinalize, markPendingFinalize, clearPendingFinalize.
  • lastRunEndedInError field, recordAgentEndError, lastAgentRunWasError.
  • The stopReason === "error" branch in agent_end.
  • The pending-flush blocks in input and session_shutdown.
  • The agent_start handler becomes empty (it only cleared the pending flag).

This is the smallest change that removes the subtle rule the original recommendation wanted to house.

Design B: read the transcript from the session

Drop messages from SessionState and read the interaction at settle. This removes the last interaction field and makes the transcript survive a reload.

Mark the boundary

At the start of a new interaction, record where it begins. Two options:

// before_agent_start, non-steering only
interactionStartId = ctx.sessionManager.getLeafId();      // in memory
// or, survives reload:
pi.appendEntry("sillajje/interaction", { start: Date.now() });

Read the slice at settle

const branch = ctx.sessionManager.getBranch();            // full path, append-only
const start = branch.findIndex((e) => e.id === interactionStartId);
const entries = start >= 0 ? branch.slice(start + 1) : branch;
const messages = entries
  .filter((e): e is SessionMessageEntry => e.type === "message")
  .map((e) => e.message);
const interaction = deriveInteractionData(messages);

Use getBranch(), not buildContextEntries(). getBranch keeps every ancestor, so a mid-interaction compaction does not hide the pre-compaction messages. buildContextEntries drops summarized entries.

before_agent_start does not fire for a steer or follow-up queued while streaming (agent-session.js:859 queues and returns before the emit at :915). A steer is therefore inside the current slice, which matches the fold-in rule. A follow-up is also inside the same slice, because the loop drains it before the final agent_end. See the caveat below.

Caveats

The stale-comment risk

Everything here rests on agent_settled reaching the extension. The source says it does; the comment says it does not. Prove it with a log line in a real TUI session before committing to the design. If it does not fire, fall back to the state machine from the first report.

Follow-up semantics may change

The existing test "followUp creates its own change" emits agent_end manually after each segment. In real pi the loop drains the follow-up inside the same run and emits one final agent_end, so the current code would already produce one change, not two. Design A does not change that; it just makes it explicit. If one-change-per-follow-up is required, the boundary must be detected at the follow-up's message_start, not at settle. Decide which semantics you want, then adjust the test.

Reload and resume mid-interaction

An in-memory interactionStartId is lost on reload. pi.appendEntry survives it, at the cost of one extra session node per interaction. The high-water-mark variant (record the last stamped entry id) needs no start marker but must handle entries added by compaction or other extensions.

Session writes from before_agent_start

pi.appendEntry advances the session leaf. Verify that appending before the user message lands does not disturb pi's own bookkeeping. The read-only path (in-memory id) avoids the question entirely.

Blocking

agent_settled is awaited, so stamping at settle blocks the idle transition just as stamping at agent_end does today. No regression, no improvement.

Open questions

  • Does agent_settled reach handlers in your TUI session? Log it. If yes, Design A.
  • Design A or B? A is a tiny diff and captures the correctness win. B removes the transcript holder and survives reload. Start with A.
  • What is a follow-up, one change or part of the current one? The answer decides whether settle-only stamping is enough.
  • Marker or high-water mark? In-memory start id is simplest; appendEntry persists across reload; the last-stamped id needs no start event.
