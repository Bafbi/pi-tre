Summary

The diagnosis was possible only by reading jj's operation store and inferring the fallback subject. The fold's own error text and the sub-generator warnings never reached a file we can read. pi already provides the channel — pi.appendEntry(customType, data) writes a non-context custom entry — and sillajje already uses it for sillajje/base, sillajje/seed, and sillajje/stamp.

Add one diagnostic entry type and write it from the two places that already see everything: the shared status sink and each action's completion. Failures are always recorded; phases and success detail can be gated.

The channel pi already gives us

pi.appendEntry() persists non-context session data. The session format calls it a CustomEntry:

{"type":"custom","id":"h8i9j0k1","parentId":"g7h8i9j0","timestamp":"…","customType":"sillajje/action","data":{…}}

It does not enter LLM context, may be rendered by a registered entry renderer, and is identified on reload by customType. Sillajje already writes three types this way, so the wiring and the read-back helpers exist.

Proposed record

One write per action invocation, plus one per failure. A single sillajje/action type keeps the schema in one place; a distinct sillajje/error type would make failures greppable without a discriminator.

{
  "customType": "sillajje/action",
  "data": {
    "action": "fold",                 // fold | stamp | sync | seed | archive | new
    "phase": "fold|error",           // fold_start | fold_done | fold_failed
    "ok": false,
    "input": { "session": "…", "onto": "trunk()", "named": null,
               "update": null, "exclude": [".scratch/*"], "noMarker": false },
    "resolved": { "base": "qsnwx…", "tip": "lrvrs…", "target": "trunk()" },
    "source": { "sessionKey": "…", "wsPath": "…" },
    "diff": { "files": 312, "omitted": [{ "path": "blocks.json",
              "changes": 214000, "reason": "too-large" }],
              "estimatedTokens": 12000 },
    "generator": { "model": "opencode-go/deepseek-v4.1-flash",
                   "headerFellBack": true, "summaryFellBack": true,
                   "attempts": 3 },
    "error": { "step": "bookmarkSet", "code": 2,
               "message": "invalid value 'slj/f/…' … Syntax error" },
    "result": { "rev": null, "marker": null, "bookmark": null, "pushed": [] }
  }
}

The useful-detail set is exactly what was missing for 01a107e9: the sub-generator fallback flags, the diff-budget manifest, the resolved base and tip, and the failing step with jj's message.

Where to write it

  1. The status sink. createStatusSink in extensions/sillajje/src/index.ts already receives every phase, info, warning, and error. Appending on warning and error alone captures the two missing fault classes with no per-action work.
  2. Action completion. The fold, stamp, and sync handlers already branch on result.ok. One appendEntry per branch writes the input, the resolved refs, and the result.
  3. The sub-generator result. header.fellBack and summary.fellBack already exist in fold.ts and drive the warnings. Carry the flags, not a boolean.
  4. The diff budget. collectDiff returns the omitted-file list; emitDiffCondensed turns it into a message. Persist the structured list, not the rendered sentence.

Open questions

  • Type naming. One sillajje/action with an action field, or sillajje/fold, sillajje/stamp, …? One type is easier to query; per-action types are easier to render differently.
  • Volume. Always write the failure record. Gate the success record and every phase behind debug, or always write one line per invocation? A fold with 55 commits runs ~8 jj commands; per-command tracing is too much for the session.
  • Error detail. Persist jj's full stderr and the exact argv, or a trimmed step + code + message? The full argv can be long and may contain paths.
  • Correlation. Stamp the record with the action's change id or op id so it joins the jj op log after the fact? The op id is only known after the last command.
  • Read-back. Do you want a /sillajje:log command that prints the last action records, so a user can paste them without opening the jsonl?
  • Load path. How should the dev tree reach ChunkEdge: pi -e /home/neudeline/code/pi-tre, a local package declaration in .pi/settings.json, or a pinned git ref plus pi update --extensions?
