Fold markers — why record a base, and how to make it simple

The marker is useful in every fold, land included. The only real flaw was uniqueness: one ref per branch, shared by every source. Key it per (branch, source) and look it up by ancestry, and the special cases disappear.

Summary

A fold onto a review branch always publishes the increment: the folded change is a child of the review head, so its diff is review-head → session-tip whatever the base. The base does not change the tree. It changes which source commits get replayed to get there, and that range becomes the Ref: line and the sub-generator's diff.

  • Recorded base (the source tip last published): replay only the new work.
  • Fork-point base (derived from the graph): replay the whole source range.

The recorded base is never harmful. It buys two things: replaying only the new range (no O(N) re-duplication and no spurious conflict on already-published lines), and a Ref:/summary equal to the change actually appended. So it should be recorded in every fold, not only the named-review ones.

The old design made the marker a single ref sillajje/folded/<branch>, shared by every source folding onto that branch. The fix is to stop forcing uniqueness: keep one marker per source under slj/f/<dest>/<source>, and pick the applicable one by ancestry — the tip-most recorded tip that is an ancestor of the source. A fold moves its own source's marker; a handoff writes a new one and leaves the old, so a fork can never steal it.

One command covers both flows: fold -o <target> [--named <branch>] [--land] [--push] [--archive] [--exclude <path>] [--no-marker]. Always record the marker; --no-marker forces the fork point when you want a fresh aggregate.

Why a base

fold runs three steps in one jj transaction (packages/sillajje-core/src/fold.ts):

  1. jj new <target> — the empty folded change F, a child of the review head.
  2. jj duplicate <base>..<tip> -d <target> — copies of the source range placed on the review head.
  3. jj squash <root>::<head> --into F — collapse the copies into F.

Step 3 collapses to review-head → tip, so the tree is the same either way when nothing has diverged. The base decides the range in step 2. With the fork point, that range is the whole session; with the marker, only the commits since the last fold. The mechanism is exact — the difference shows up when the review branch has diverged.

Base comparison

Scenario: the session has A (x: base→one) then B. A was folded onto review. A reviewer then edited the review branch (R). Step through the fold for each base.

Scenario A (no divergence): both bases land the same tree; the fork-point base only makes the Ref: span the whole session. Scenario B (diverged, new work elsewhere): the fork-point base replays A onto the reviewer's x and conflicts on a line B never touched — the spurious conflict the marker prevents. Scenario C (your case): the new work edits the same line the reviewer did, so both bases conflict — legitimate, and the marker does not hide it.

The uniqueness flaw

With one marker per branch, two sources folding onto the same review branch share a cursor. Session 1 publishes A, session 2 publishes B, and sillajje/folded/review can only hold one of them. Keying by session gives each its own, but then a handoff breaks: /sillajje:new -s @ hands the history to a new session key, which misses the old record unless the lookup is by ancestry. A renamed or rewritten source has the same problem. That is the trade recorded in ADR 0006.

Both constraints drop if markers are non-unique and looked up by ancestry rather than by exact key. Multiple markers per destination are fine; the lookup asks "which recorded tip is the tip-most ancestor of my source?" and gets the right one whether the key matches or not. The name is per source, so a fork cannot overwrite a sibling's marker, and a handoff simply finds the predecessor's by ancestry.

Proposed model

Record

Every successful fold sets slj/f/<dest>/<source> to the source tip it published. <source> is the session key for a session source, or the source bookmark name (else the tip's change id) for a rev source. Each source moves its own marker; the store holds one per source.

Look up

For destination D and source tip S, take heads(::S & slj/f/D/*) — the tip-most recorded tip that is an ancestor of S. No match means a first fold for this source: base = fork point.

Bypass

--no-marker ignores the store and bases on the fork point, then records nothing. The escape hatch for a deliberate fresh aggregate.

Consequences: concurrent sources no longer collide, whether they fork from published or unpublished bases; handoff, rename, and rewrite all resolve by ancestry; --update is redundant with -o <branch> --land; and a missing marker is a normal first fold, not an error. The lookup is the only new logic, and it is one revset. The trade: a handoff (or a renamed source) writes a new marker and leaves the predecessor's behind. The old one is harmless — nothing descends from it — but it lingers until pruned.

Every fold carries exactly its own file: the s1 source touches x.txt, the s2 source touches y.txt. The handoff step runs from a new session key sNew: it finds A2 by ancestry, writes slj/f/review/sNew, and leaves s1's marker behind. The append is still only H.

Why per-source: a fork looks like a handoff

Reusing the base marker's suffix keeps the name stable across a handoff, but it also lets a fork from a published base take over that marker. From ancestry alone the two are identical: both have the published commit as an ancestor. In a handoff that is right; in a fork it steals the original source's cursor. That is why the name is per source.

Walk the fork: s1 publishes A, s2 branches from A and publishes B (a sibling, not a continuation), then s1 continues with A2. Toggle the naming scheme to compare.

Reuse mode: s2's fold moves slj/f/review/A to B. s1's next fold finds no ancestor marker, bases on the fork point, replays A on top of a review head that already holds B, and conflicts on x.txt. Per-source mode (chosen) writes slj/f/review/s2 and leaves s1's marker alone, so s1 folds only A2 — clean. The price is a new marker name on handoff.

What it changes

Earlier decisionUnder the simplified model
Q1 — marker created only by --namedEvery fold records one. Non-unique per source, so creation is no longer an ownership claim.
Q2 — accept that -o X cannot be updated laterDropped. -o X records too, so a later -o X --land appends only the new work.
Q3 — exclude sillajje/* from --land's bookmark countKept. Independent and still correct.
Q4 — --update errors with no markerDropped. No marker is a normal first fold; base = fork point.
Q5 — error on a foreign markerDropped. Foreign markers are not ancestors, so the lookup ignores them. No ownership conflict.
Q6 — --named refuses to hijack an existing branchKeep the guard the other way: --named B still must not move an existing B sideways or backwards. jj already refuses that move.
--update modeBecomes -o <branch> --land. The --update/-o split disappears.

One existing test changes meaning: fold.test.ts "a plain fold ignores the Folded source marker and re-aggregates from the fork point" asserts the old -o behaviour. Under this model a plain -o uses the marker, so that test must assert the increment instead, and the fork-point re-aggregate becomes the --no-marker case.

Open questions

  • Source name for a rev source: bookmark name when it has one, else the tip's change id. A change-id name accumulates a marker per new tip; prune by keeping only the tip-most ancestor per name?
  • Pruning: orphaned markers linger as bookmarks. Delete them when no live source descends from them, or leave them (ancestry already ignores them)?
  • Keep --update as an alias for -o <branch> --land, or remove it outright?
