Spec

The ADR final amendment was added in this diff, so it is the spec. The design report supplies the rationale and the "What it changes" table.

P1 — Prefix match can read a nested destination's markers (implementation looks wrong)

ADR 0006, line 70:

"a fold bases on heads(::<source-tip> & slj/f/<dest>/*), the tip-most recorded tip that is an ancestor of the source."

The code (fold.ts:322–326) uses a string prefix:

const prefix = `${FOLDED_MARKER_NAMESPACE}/${dest}/`;
const markers = (await jj.bookmarks({ cwd })).filter(
	(bookmark) =>
		bookmark.remote === undefined && bookmark.name.startsWith(prefix),
);

startsWith matches across /. If a user folds with --named review/extra, that writes slj/f/review/extra/<source>. A later fold with destination review matches those markers, because the name starts with slj/f/review/. The lookup can then base on a marker that belongs to a different destination. Match exactly one path segment after <dest>, or split the name and compare the destination segment.

P2 — --named "" writes a marker it never reads (partial requirement)

ADR 0006, line 68:

"every fold records a marker, and every fold bases on one."

Design report, "What it changes": "Every fold records one."

At fold.ts:561–566, an empty --named sets destLookup = undefined, so the fold skips the store and bases on the fork point. It still writes a marker under slj/f/fold-<changeId>/<source> (fold.ts:797–806) that no later fold can address, because the next --named "" fold generates a different change id. The record half holds; the base half does not, and the marker is dead weight.

P3 — Tip-most selection is undefined for incomparable markers (edge)

ADR 0006, line 70: "the tip-most recorded tip that is an ancestor of the source". The code compares markers pairwise with isAncestor(best, commit) (fold.ts:336). That is well-defined only when the two markers sit on one ancestry line. When the source is a merge of two previously folded branches, two markers can each be an ancestor of the tip and neither an ancestor of the other; the code returns whichever it visited first. Low severity: the ADR treats a merge in the source range as linearized by the replay.

P4 — FoldResult.marker is not asked for (scope creep, minor)

ADR 0006 and CONTEXT describe the marker as the stored bookmark. No line asks fold to return it. This overlaps S5; note it as scope creep on the Spec axis too.

Open questions

  • Was --named "" (P2) meant to be usable for incremental folds? Options: (a) derive the destination from the generated change id is impossible, so document the fork-point replay as intended; (b) key the marker on the target instead when --named is empty; (c) forbid the empty form.
  • Is a bookmark name containing / a supported destination (P1)? If yes, fix the match. If no, reject / in --named.
  • Keep FoldResult.marker (S5/P4) for observability, or drop it until a caller needs it?
