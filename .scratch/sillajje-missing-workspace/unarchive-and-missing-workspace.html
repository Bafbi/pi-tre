Recovering a session whose workspace went missing

Unarchive is the recovery verb the code already names. Two gaps stop it from working, and the live-workspace guard landed this session makes one of them worse.

2026-09-25 scope: extensions/sillajje, packages/sillajje-core, packages/sillajje-workspace source: PR #19 triage review status: fixed in the 13:18 review triage

Landed. The proposed fix set below shipped in the second triage pass: Workspaces.isLive, the createUnarchive switch from lookup to isLive, and SessionState.clearMissingWorkspace() on the unarchive success path. The sections below are kept as the diagnosis that motivated it.

Summary

A session whose workspace directory is deleted mid-run is marked missing and blocked. The code tells the user to run /sillajje:unarchive to recover, but the recovery does not complete: the missing flag is never cleared, so the session stays blocked after a successful unarchive.

The PR #19 triage fix for the live-unarchive corruption adds a second problem. createUnarchive now rejects any registered workspace, and a missing workspace is still registered. So bare /sillajje:unarchive returns session … is already active exactly when the user needs it, foreclosing the recovery path the notification points at.

The landed guard rejects a registered workspace. A missing workspace is registered with a dead directory. To tell the two apart, the guard must ask whether the directory still exists, not whether jj still lists the workspace.

The two gaps

Gap 1: the missing flag survives a successful unarchive

Before PR #19, unarchiving a missing workspace recreated the directory, but the session stayed blocked. markMissingWorkspaceAndNotify is deduped on the flag, so after recovery the next tool call still hits missingWorkspaceBlockReason and before_agent_start still no-ops. Only a process restart (reset) clears it. The documented recovery never returned the session to a usable state.

Gap 2: the live guard blocks the recovery

The guard added in PR #19 reads:

if ((await workspaces.lookup(sessionKey)) !== undefined) {
	return { ok: false, reason: "active", sessionKey };
}

lookup answers "is this workspace registered?". For an externally deleted workspace the answer is still yes: jj workspace forget never ran, so jj lists the name with a root that no longer exists. The guard therefore turns the one recovery verb into an error.

The guard is correct in intent. A live workspace must not be unarchived, because unarchive runs forgetQuietly before jj workspace add and the add fails on the non-empty directory. The bug is the predicate, not the guard.

Proposed fix

1. Add Workspaces.isLive

Live means registered and the directory still lives, the same condition ensure uses to reuse a workspace. The workspace package owns filesystem knowledge, so the predicate lives there.

/** Whether the session's workspace is registered and its directory still lives. */
isLive(sessionKey: string): Promise<boolean>;
async isLive(sessionKey) {
	const name = workspaceName(sessionKey);
	const found = (await jj.workspaces(jjOptions)).find((w) => w.name === name);
	return found?.root !== undefined && existsSync(found.root);
},

2. Guard unarchive on isLive

A live workspace is rejected; a missing one falls through to unarchive, which forgets the stale registration and recreates the directory.

if (await workspaces.isLive(sessionKey)) {
	return { ok: false, reason: "active", sessionKey };
}
const workspace = await workspaces.unarchive(sessionKey);

3. Clear the missing flag on unarchive

Add SessionState.clearMissingWorkspace() and call it in handleUnarchive on the success path, beside setActive() and setWorkspacePath().

clearMissingWorkspace(): void {
	this.missingWorkspace = false;
}

Tests

  • Workspace: isLive is true for a present directory and false after the directory is deleted. This is the unit that pins the predicate.
  • Core: the existing rejects an already-live session test switches from lookup to isLive; add unarchives a registered-but-gone workspace asserting unarchive is called.
  • Integration: delete the workspace directory, run bare /sillajje:unarchive, assert the directory is recreated, the input handler returns continue, and no missing-workspace block fires.
  • State: clearMissingWorkspace returns isMissingWorkspace() to false.

After the fix the documented flow works end to end: delete the directory, get the notification, run bare unarchive, keep working. The live-workspace corruption stays closed because a genuinely live workspace still fails the guard.

Adjacent gaps

These are not required for the recovery to work. They are the same live-versus-registered confusion in other call sites, and they belong in the same change or the one after.

  • resolveTarget treats a registered-but-gone workspace as resolvable (packages/sillajje-workspace/src/index.ts:371). It returns { ok: true, wsPath: found.root } without an existsSync, so sync, fold, and cross-session stamp can target a dead path. Aligning it with ensure's reuse condition would make the port tell one story.
  • Manual /sillajje:stamp on a missing workspace is not gated on isMissingWorkspace(). stampManual only checks that sessionId and wsPath exist, and the dead path is still stored, so the command reaches jj and fails with a jj error instead of the block message the auto-stamp path uses. The sessionDefault gate does not catch it: a missing workspace is still isActive().

Open questions

  • Is unarchive the whole recovery, or should the session self-heal? The notification already promises unarchive. Recommendation: keep unarchive as the explicit verb and clear the flag there. Auto-recreate on the next interaction hides a repository change the user may want to see.
  • Should setActive() clear the missing flag everywhere, or only unarchive call clearMissingWorkspace()? Recommendation: only unarchive. A plain setActive() is reused by the archived-session path, where the flag was never set.
  • Ship the adjacent gaps here or separately? Recommendation: resolveTarget with this change, because it is the same predicate, and the manual-stamp gate as a separate small change so each has its own test.
