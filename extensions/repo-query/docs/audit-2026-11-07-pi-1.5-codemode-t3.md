# Audit: repo-query against pi 1.5.0, code mode, and T3 Code

Date: 2026-11-07
Scope: `extensions/repo-query`, `packages/pi-subagent`, `packages/pi-config`
Baseline: pi 1.2.0 before the upgrade, pi 1.5.0 after it.
Method: source reading, type and docs diff, published package inspection, T3 Code binary inspection. No live pi or T3 session was run.

Three delegates produced the raw findings. Their reports were transient and are not committed. The conclusions below were re-checked against the installed package, the 1.5.0 package, and the T3 binary. Corrections are noted inline.

## Update: T3 delegate integration

T3 registers its orchestrator tools into pi as `mcp__t3-code__<name>`. Verified in the T3 binary:

- `delegate_task`, `orchestrator_capabilities`, and `task_status` are registered with `exposure: "direct"`.
- Every other T3 tool is registered with `exposure: "deferred"`.

So a pi extension under T3 can call `ctx.executeTool("mcp__t3-code__delegate_task", args, { signal })`. That is the integration point.

The current explorer cannot use it, because `repo-query` spawns a child `pi --mode json` process without T3's `--extension` argument. The child has no T3 tools. A T3-aware backend would run in the parent pi process and call `ctx.executeTool`.

Two constraints decide whether it is a good fit:

- The delegate's working directory is the T3 project or a worktree from the parent commit, not the tempspace. The task must pass the clone path and the delegate must read outside its working directory.
- A delegate is a full agent thread, not a read-only explorer. It has its own tools and UI, and it can edit files.

A safe design is a third explorer backend: use `delegate_task` when `mcp__t3-code__delegate_task` is registered, otherwise keep the child pi process.

Implemented in `src/t3-delegate.ts`, selected by setting the `explorer` config key to `auto`. The default is `process`, so the broader delegate agent is opt-in. The delegate is a T3 thread, so the exploration is visible in the UI. The task carries absolute clone paths and asks for read-only behavior. The delegate runs with full access because T3 has no per-delegate tool allowlist and approvals on every codemode call make it unusable. The prompt restricts codemode to `read`, `grep`, `find`, and `ls`, and forbids `bash`, `edit`, `write`, and `repo_query`.

The delegate title starts with `read-only:`. T3 sets the delegate session name to that title, and `src/read-only-delegate.ts` checks `ctx.sessionManager.getSessionName()`. The `tool_call` hook in `src/index.ts` allows only `read`, `grep`, `find`, `ls`, `codemode`, and `tool_search` for that session. Everything else is blocked, including `write`, `edit`, `bash`, `powershell`, `repo_query`, and T3 control tools. pi applies the hook to nested codemode calls, so `tools.write` inside a script is blocked. This covers pi delegates only. A delegate on another provider does not load this extension. The child pi process remains the fallback and keeps its `--tools` allowlist.

The delegate backend is covered by a fake `executeTool` pipeline test and by live T3 pi provider runs. The live run used the `read-only: repo_query: ...` title, returned 20 verified findings, and exercised the guard allowlist inside codemode.

## 1. Version posture

| Item | Value |
| --- | --- |
| Catalog `pi-dev` | `^1.2.0` |
| Installed | 1.2.0 |
| Published `latest` | 1.5.0 |
| Upgrade blockers | none |

Every API that `repo-query` touches survives from 1.2.0 to 1.5.0. The tool fields the audit recommends also exist in 1.2.0, so the code-mode work does not require the upgrade first.

One claim in the d1 report is wrong: `dist/core/extensions/types.d.ts` is not byte-identical between 1.2.0 and 1.5.0. It differs by 31 lines. The differences are new, not breaking:

- `ToolRenderContext`, `MessageRenderOptions`, and `EntryRenderOptions` now extend `KeybindingHints`.
- `ctx.ui.custom()` accepts `blocked`.
- message render options gain `messageId` and `timestamp`.

The 1.5.0 breaking change, argument validation moving to `@earendil-works/pi-schema`, does not affect this repo. `RepoQueryParams` (`src/index.ts:45`) uses only `Type.Object`, `Type.Array`, and `Type.String` with `minItems` and `maxItems`. No `Type.Refine`, `Type.BigInt`, `Type.Undefined`, codecs, or `Format.Set` appear in `extensions/repo-query/src`, `packages/pi-config/src`, or `packages/pi-subagent/src`.

## 2. Extension interface usage

### What is already right

- `promptSnippet` and `promptGuidelines` exist, and every guideline names `repo_query` (`src/index.ts:141-147`). pi appends guidelines flat under `<rules>`, so the explicit name is required.
- Every `onUpdate` carries `content` and `details`, and `details` has one type, `RepoQueryDetails` (`src/index.ts:213-218`). This matches the tool result contract.
- `ctx.cwd`, `ctx.isProjectTrusted()`, and the `sessionManager` methods used in `src/tempspace.ts:38` and `src/debug.ts:180-196` all exist in 1.5.0.
- Cancellation is threaded through the clone, the explorer, and the child process.
- Clone publication is atomic, and the in-flight registry dedupes concurrent clones (`src/clone.ts`).
- Config loading is trust-gated through `@pi-tre/pi-config`.

### Gaps

**Must: an exploration failure is reported as success.**
When `runExplorer` returns an error, the code sets each repo to `exploration_failed` (`src/index.ts:537-550`) and then returns a normal tool result (`src/index.ts:555-574`). No `isError` flag is set. The model reads a failed exploration as an answer. This affects direct calls, not only scripts.

**Must: the all-failed path throws and drops the data.**
`throw new Error(parts.join("\n"))` at `src/index.ts:469` reports the error, but it discards `details` and `structuredContent`. The per-repo statuses and the "did you mean" suggestions exist at that point (`src/index.ts:439-466`). Returning `{ content, details, structuredContent, isError: true }` keeps them for the model, the TUI, and scripts.

**Must: no `outputSchema`, so scripts receive prose.**
The tool returns `content` text and untyped `details`. A code-mode script calls `tools.repo_query(...)` and receives one markdown string. `toScriptValue` in the code-mode adapter returns `structuredContent` only when the tool declares `outputSchema` (1.2.0 `dist/extensions/codemode/execute.js:363-375`, 1.5.0 `:413-425`). Otherwise it returns the text.

**Should: empty phase updates are invisible outside the TUI.**
`emitPhase` sends `content: [{ type: "text", text: "" }]` (`src/index.ts:215`). The TUI renders from `details`. T3 renders only `content` text, so every phase update is a no-op there. Emit one line per phase instead, for example `Cloning facebook/react...`.

**Should: `result.killed` now covers more than a timeout.**
In 1.5.0, `killed` is true on timeout, abort, and `maxBuffer` exhaustion (`docs/extensions.md:1890`). `src/clone.ts:383-385` maps it unconditionally to "timed out after 120000 ms". Use `result.truncated` to tell a buffer cut from a timeout.

**Should: import key hints from the render context.**
`src/render.ts:4` imports `keyHint` from the package. That import can resolve the extension's own copy, which does not see the host keybindings. 1.5.0 injects `context.keyHint` and `context.keyText` (`ToolRenderContext extends KeybindingHints`). Use the injected functions.

**Should: declare tool annotations.**
The tool clones remote repositories, runs `git`, calls the GitHub API, and spawns a child `pi` process. Declare `annotations: { readOnlyHint: false, destructiveHint: false, idempotentHint: true, openWorldHint: true }`. Permission extensions use these hints, and the defaults assume the worst.

**Should: migrate TypeBox imports to `typebox`.**
1.5.0 documents `typebox` and keeps `@sinclair/typebox` as a legacy alias (`docs/extensions.md:161-166`). The alias works. The reason to move is that a resolved package copy is exactly the drift the keybinding note warns about. This is a mechanical change.

**Nice: argument completions for `/repo-query-debug`.**
Add `getArgumentCompletions` for `on`, `off`, `status`, `dump`, and `toggle`.

### Subagent transport

`repo-query` passes `createProcessBackend()` explicitly (`src/explorer.ts:110-113`). The child command is `pi --mode json -p --no-session --tools ...` (`packages/pi-subagent/src/process-backend.ts:234-268`). Every flag still exists in 1.5.0.

`packages/pi-subagent` also ships an in-process backend built on `createAgentSession`. Do not switch yet. Two blockers remain in that backend:

- The child keeps custom and extension tools active unless `excludeTools` is passed, so a child could recurse into `repo_query`.
- It reports `overflow: false` unconditionally (`src/in-process-backend.ts:168`), so the 32 MiB child output cap is lost.

The process backend also gives crash isolation for an LLM that runs `bash` in cloned vendor code. Keep it.

## 3. Code-mode fit

Verdict: `repo_query` is not optimized for code mode. It works from a script only because pi falls back to the text content.

What a script sees today:

```js
const text = await tools.repo_query({ query: "...", repos: ["a/b", "c/d"] });
// "# Answer: ...\n<prose up to 8000 chars>\n\n## Issues\n- **c/d**: not_found\n  - Did you mean: c/dd?"
```

What that blocks:

| Job | Today | Needed |
| --- | --- | --- |
| Retry on a suggestion | Regex over `## Issues` prose | `repos[].suggestedRepos` |
| Branch retry | The suggestion is inside `error` text (`src/clone.ts:442-462`) | `repos[].suggestedBranches` |
| Per-repo branching | Parse markdown | `repos[].status` |
| Filter by path or line | The answer is prose | `findings[]` with `repo`, `path`, `line` |
| Attribute a claim to a repo | One answer for all repos | Per-repo answer or per-repo call |
| Budget on cost | No usage | `usage.cost` |

### Errors

The current shape is the worst of both:

- Total failure throws (`src/index.ts:469`). A `Promise.all` rejects and cancels sibling calls. Scripts must use `allSettled`.
- Partial and exploration failure return a normal result with no `isError`.

`toScriptValue` has a subtlety. When a tool declares `outputSchema` and returns `structuredContent`, an `isError` result resolves to the data. Without `outputSchema`, an `isError` result throws in the script. So the fix must land as one change: add `outputSchema` and `structuredContent` first, then return `isError: true` for failures.

Target error table:

| Case | `status` | `isError` | Script result |
| --- | --- | --- | --- |
| All repos explored | `ok` | false | resolves |
| Some repos failed | `partial` | false | resolves, inspect `repos[]` |
| No repo explored | `failed` | true | resolves, `answer: null` |
| Invalid arguments | n/a | pi validation | rejects |

### Batching

One call with N repos is the right shape for a comparison question. It is the wrong shape for independent questions:

- Clones run in sequence (`src/index.ts:350-416`). Five 120 s clones delay the subagent by up to 10 minutes.
- GitHub validation also runs in sequence, and the cache is filled after the await (`src/index.ts:282`), so a parallel fan-out can hit the rate limit.
- One subagent produces one answer, so claims cannot be attributed to a repo.
- `resolveModel` checks only the first repo (`src/config.ts:60-82`).

A fan-out of single-repo calls runs clones in parallel, dedupes the same clone through the registry, attributes each answer, and applies the per-repo model. The tool description and `promptGuidelines` should teach both shapes: one call per repo for independent questions, one batched call for comparison.

### Streaming

Under code mode, nested `onUpdate` events have no consumer. Each update re-sends the full answer and the full thinking text, so the payload grows with the square of the text. Throttle to a few per second and send only the tail of `thought`. Keep the phase updates for direct calls.

### Output budget

- The subagent answer is capped at 8000 characters (`src/explorer.ts:15`).
- pi truncates the formatted text at 50 KB and 2000 lines (`src/output.ts:115-118`). The cut removes the tail, which holds `## Issues` and `## Warnings`.
- Code-mode script output defaults to about 40,000 characters, with hard caps of 16 Mi characters and 100,000 items.

For the model, keep the prose. For scripts, return `structuredContent` uncut and keep it small. Do not put an 8 KB prose answer in every structured result.

### Usage

`toAgentUsage` (`src/index.ts:74-89`) reports honest `input`, `output`, `cacheRead`, `cacheWrite`, `totalTokens`, and `cost.total`. The per-component cost fields are set to 0, which reads as "free" rather than "unknown". `turns` is dropped because pi's `Usage` has no slot for it. Add `cost.totalFromProvider` when the subagent's totals come from a provider rather than a catalog estimate.

Code mode adds nested usage to the calling tool result, so a `repo_query` cost is counted once in the `codemode` row. A script cannot see the per-call cost. Put `usage` in `structuredContent` so it can budget.

### Session and concurrency

- `cachedTempspace` is module-level (`src/tempspace.ts:11`). It is safe under T3, which uses one pi process per thread, and under code mode, which shares the session. It would leak across sessions if one process ran several.
- The session branch scan is blind under code mode because nested results are not transcript entries. The session-file hash path still produces a stable tempspace.
- On 1.5.0, at most two code-mode workers run per process (`PI_CODEMODE_MAX_WORKERS`). A `repo_query` call holds a worker for its whole run, up to 120 s per clone plus 300 s for the subagent. Scripts that fan out should set `timeout_ms`.
- The tool itself does not cap subagent processes. A script can start N.

### Target result shape

```ts
{
  status: "ok" | "partial" | "failed",
  query: string,
  model: string | null,
  answer: null | {
    text: string,
    complete: boolean,
    findings: Array<{
      repo: string,
      path: string,
      line: number | null,
      claim: string,
      verified: boolean
    }>
  },
  repos: Array<{
    identifier: string,
    displayName: string,
    branch: string | null,
    status: "success" | "archived" | "not_found" | "clone_failed" | "exploration_failed" | "skipped",
    localPath: string | null,
    warnings: string[],
    error: string | null,
    suggestedRepos: string[],
    suggestedBranches: string[]
  }>,
  usage: null | { input: number, output: number, totalTokens: number, cost: number },
  tempspacePath: string
}
```

The subagent ends with one JSON block. Parse it, verify each `path` exists and each `line` is in range, and fall back to prose when parsing fails. Render the model's text from the same data.

Keep `exposure: "direct"`. The common case is one question, and the progress row helps. `codemode.mode` already decides whether declared tools stay visible. Moving to `codemode` exposure would force a script for every question.

## 4. T3 Code integration

### How T3 runs pi

T3 spawns the pi CLI as a child process and speaks pi's RPC mode over JSON lines. It does not use the SDK or JSON mode.

Verified in the T3 binary at `~/.t3/runtime/versions/0.1.8-nightly.20261106.4262/t3`:

- `buildPiRpcLaunch()` builds args starting with `["--mode", "rpc"]`.
- The command is `PiSettings.binaryPath || "pi"`.
- `openSession()` writes its own extension to `pi-t3-mcp-extension.ts` and passes `--extension <path>`.
- The working directory is the T3 worktree.
- pi creates its own session file. T3 reads `get_state().sessionFile` and later uses `switch_session`, `new_session`, and `fork`.
- `MAX_STRUCTURED_TOOL_OUTPUT_BYTES = 65536`.

The Pi provider is disabled on this machine. `~/.t3/caches/pi.json` says `"enabled": false, "installed": false, "status": "disabled"`. No live end-to-end run was possible.

### What stays live

| API | Under T3 |
| --- | --- |
| `registerTool`, custom commands, session hooks, `pi.exec` | live |
| pi code mode | live, enabled by `defaultTools: ["+codemode"]` in `~/.pi/agent/settings.json` |
| `ctx.mode` | `"rpc"`; `ctx.hasUI` is `true` |
| `ctx.ui.confirm/select/input/editor` | live, rendered as T3 approval cards |
| `ctx.ui.notify` | live only while a turn is active |
| `ctx.ui.setStatus` | live |
| `ctx.ui.setWidget`, `setTitle`, `setEditorText` | ignored |
| `renderCall`, `renderResult` | never called |
| `details` on a dynamic tool | dropped; only `bash` and `edit`/`write` are read |
| `content` and `structuredContent` | forwarded, structured content capped at 64 KiB |
| `onUpdate` partial `content` | reaches the tool row |

### What that means for repo-query

1. The rich TUI renderer in `src/render.ts` is dead code under T3. Keep it for the TUI, but do not rely on it.
2. `/repo-query-debug dump` loses its output. It uses `setEditorText` and `notify`, and a handled slash command starts no turn. `setStatus` survives. Route the dump through a `ui.editor` dialog or a tool result.
3. Empty phase updates show nothing. See the must-fix list.
4. `details` is invisible in T3. Move data that T3 or scripts need into `structuredContent`.
5. The child `pi` spawn works because `getPiInvocation()` resolves `process.execPath` plus `argv[1]`. It can skew from T3's configured `binaryPath`. Resolve in this order: an explicit setting, `process.argv[1]` when it is a pi bundle, then `PATH`.
6. The T3 worktree has no `.pi` directory and is not in `~/.pi/agent/trust.json`. `ctx.isProjectTrusted()` is `false`, so the project config layer is dropped. The global `~/.pi/agent/configs/repo-query.json` still applies. It sets `defaultModel` to `opencode-go/deepseek-v4.1-flash`.
7. The extension loads from the installed global package, `~/.pi/agent/git/github.com/Bafbi/pi-tre`, because `~/.pi/agent/settings.json` has `packages: ["git:github.com/Bafbi/pi-tre"]`. The worktree's root `package.json` `pi.extensions` field is not an auto-discovery location. It only applies when the package is installed. The installed `extensions/repo-query/src` is identical to this worktree today, so nothing is stale now. Future edits will not reach T3 until `pi update --extensions` runs.
8. `pi.exec("git", ["clone", ...])` and the child pi spawn are not tool calls, so T3's approval extension never gates them, in any runtime mode. A tool with `openWorldHint` is still gated as a tool call. The work it does inside `execute` is not.
9. One pi process per T3 thread means module state does not bleed between threads.

### T3 Code Mode is a different sandbox

T3's Code Mode is OpenCode's. pi's code mode is QuickJS inside the pi process. They do not share a tool registry.

`repo_query` is reachable from the model and from pi code-mode scripts. It is not reachable from OpenCode's `execute` catalog. The only bridge is MCP: T3 exposes its own tools to both sides over MCP. To reach the OpenCode side, publish `repo_query` as an MCP server as well.

## 6. Open decisions

1. **Upgrade pi now or after the result-shape change?** Recommend now. There are no blockers, and the upgrade brings `pi.exec` hardening. The result-shape change does not need it.
2. **Do failures resolve or reject for scripts?** Recommend resolve with `status` and `isError`. A rejection cancels siblings under `Promise.all`. Document the status check.
3. **One batched call or one call per repo?** Keep both. Recommend per-repo for independent questions and batched for comparison. The per-call clone cost is the deciding factor.
4. **Keep `direct` exposure?** Recommend yes.
5. **Publish as MCP?** Only if the OpenCode side must call `repo_query`. It adds a second surface to maintain.
